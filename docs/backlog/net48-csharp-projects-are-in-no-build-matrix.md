# The net48 C# projects are in no build matrix, and one of them does not build

`CorpusProjectDiscovery` scans two roots:

```csharp
Scan(repositoryRoot, ["CSharp", "dotnet"], "*.csproj", "SDK-style C# corpus");
Scan(repositoryRoot, ["VB.NET"],           "*.vbproj", "VB.NET corpus");
```

`CSharp/dotNetFramework/` is neither. All fourteen project directories under
`CSharp/dotNetFramework/v4.8/` are therefore built by no test, and
`CorpusProjectBuildTests` — the gate that makes "0 errors and 0 warnings" mechanical — never sees
them.

**`CSharp_v1.0` does not currently build.** Under Visual Studio's `MSBuild.exe`:

```
obj\Debug\.NETFramework,Version=v4.8.AssemblyAttributes.cs(4,12): error CS8022:
Feature 'namespace alias qualifier' is not available in C# 1.
Please use language version 2 or greater.
```

`1 Error(s)`. The offending file is generated by MSBuild, not authored here: it emits `global::`,
which `LangVersion=1` rejects.

## Why it matters

The corpus's central claim is that every project builds clean at a declared SDK/TFM/language
coordinate, and that the claim is checked rather than asserted. For these fourteen it is asserted.
`AGENTS.md`'s summary states it without qualification — "every project builds at 0 errors and 0
warnings" — and that is false today.

The gap is not uniform, and the smaller half has no excuse:

- **Eleven are legacy non-SDK** and need Visual Studio's `MSBuild.exe`; `dotnet build` resolves none
  of their `PackageReference` items and fails with `CS0246`. A matrix entry for them needs a
  different host than the rest of the suite, which is the real reason they were left out.
- **Three are SDK-style** — `CSharp_v1.0-Unsafe`, `CSharp_v8.0`, `CSharp_v8.0-Unsafe` — and build
  with `dotnet build` like everything already in the matrix. Nothing about the toolchain keeps them
  out.

`CSharp_v8.0` is the sharpest case: nine net48 VB `library` projects project-reference it, and
`CorpusProjectBuildTests` now prebuilds it in `[ClassInitialize]`. So it is already built by the
suite, as a dependency, without being a project the suite holds to the bar.

## Evidence

`GenerateTargetFrameworkAttribute` does not occur in `CSharp_v1.0.csproj`.
`docs/design/language-feature-showcase-design.md` records this exact hazard and its fix —
`GenerateTargetFrameworkAttribute=false` — but as guidance for *probe* projects; the tracked project
file never adopted it. `scripts/verify-feature-floors.cs` sets it and so reports `CSharp_v1.0`'s rows
without trouble, which is why the failure is invisible from the probe side too.

The other ten legacy projects build green under VS `MSBuild.exe`.

## Suggested fix

Three steps, increasing in cost, and the first two are worth doing regardless of the third:

1. **Fix `CSharp_v1.0`** by adding `GenerateTargetFrameworkAttribute=false`, the remedy the design
   doc already names. One property.
2. **Add the three SDK-style net48 projects to the matrix.** They need no host the suite does not
   already have, and `CorpusProjectDiscoveryTests` is where the expected list lives.
3. **Decide what to do about the eleven legacy ones.** They need a VS `MSBuild.exe` the corpus suite
   does not otherwise use, so a matrix entry means either a second discovery root with its own
   runner or an explicit, recorded decision that they are verified by
   `scripts/verify-feature-floors.cs` alone. Either is better than the current silence.

Until step 3 is settled, `AGENTS.md`'s unqualified claim should be narrowed to what is actually
checked.
